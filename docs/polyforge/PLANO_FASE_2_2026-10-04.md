## 2. Análise por dimensão (releitura)

### Backend — pontos consolidados

- Boas práticas presentes: injeção via `Depends`, `Settings` do Pydantic, fila
  com cancelamento pelo pipeline, reconexão para retomada ao reiniciar, datas em
  UTC com offset, métricas Prometheus, logs estruturados.
- Limitação: ainda existe uma única fila compartilhada por todos os modos.
  Em hardware com VRAM folgada isso é desperdício, mas em GPU única é seguro.
- `exclude_unset`/`exclude_none` não são usados nos dumps dos eventos SSE;
  payloads trazem chaves `null` em toda transição. Não é bloqueante, mas amplia
  o uso de banda e dificulta a tipagem do frontend.
- O manager continua sem expor capabilities por modo (texto-imagem, multiview
  e textura podem estar indisponíveis dependendo do checkpoint carregado).

### Frontend — arquitetura e lacunas

- Estrutura coerente: `api/` (cliente, hooks), `context/` (estado único),
  `components/jobs/` (formulário e galeria), `design/primitives/` (botões,
  campos, divisores). Há teste de unidade para o payload (`generation.test.ts`).
- Lacunas observadas:
  - Apenas uma página: `App.tsx` renderiza `<CreateJobForm />` e `<JobGallery />`
    em sequência. Não há rotas, biblioteca dedicada, tela de sistema nem
    configurações.
  - O viewer 3D depende de `<model-viewer>` via CDN do Google. Sem rede
    (ou com bloqueador), o componente cai em um link de download estático
    sem qualquer estado de erro ou carregamento.
  - A galeria mostra a lista atual sem paginação, busca, filtros por data
    ou detalhe expandido. O scroll cresce indefinidamente.
  - Não há detalhe do trabalho (parâmetros enviados, duração por etapa,
    arquivos derivados, mensagem de erro). O usuário tem de abrir o GLB direto.
  - Sem reutilização de parâmetros: depois de concluído, é preciso copiar
    manualmente prompt, seed e steps para nova geração.
  - Sem i18n. Todo o texto é inglês fixo; a documentação aponta
    português como necessidade.
  - Sem testes E2E. Há 5 testes Vitest, mas não rodam layout, conectividade
    simulada ou troca de modo via navegador.
  - Sem geração de tipos a partir do OpenAPI. Tipos são mantidos à mão,
    sujeitos a divergir dos schemas Pydantic.

### UI/UX — síntese visual

A identidade visual está bem resolvida (laboratório/instrumento, mono para
técnico, serif para marca, accent âmbar cirúrgico). As capturas pós-Etapa 1
mostram:

- Desktop: header fino, sidebar de 256 px à esquerda, galeria em lista com
  filtros por status, ticker inferior. Layout aproveita o espaço, mas a
  sidebar ocupa ~20 % da largura em 1440 px.
- Mobile: layout colapsa para uma coluna, sidebar vira `<details>`,
  formulário e galeria empilhados. Sem drawers laterais para parâmetros.
- Pontos de fricção remanescentes:
  - O resultado 3D não é protagonista. O viewer aparece inline dentro de
    um card de galeria, competindo com metadados técnicos.
  - Sem indicadores de etapa visíveis durante a geração. O ticker mostra
    o último evento, mas o usuário não distingue "carregando modelo" de
    "gerando geometria" de "texturizando".
  - Upload é pouco explorado: aceita clique, mas não há área de soltar,
    nem preview grande da imagem selecionada, nem feedback visual ao passar
    o mouse sobre o campo.
  - CTA principal ("Gerar modelo") coexiste com ações técnicas em
    Avançado, sem hierarquia clara para usuários não técnicos.
  - Ações pós-conclusão limitadas: visualizar e baixar; não há
    "reutilizar parâmetros", "gerar variante", "otimizar" (já existe, mas
    sem feedback de progresso), "abrir no editor".

## 5. Modernização técnica

### Geração de tipos

- Backend expõe `/openapi.json`. Adicionar `npm run gen:types` no frontend que
  consome o schema e gera `src/api/types.gen.ts`.
- Substituir gradualmente `api/types.ts` pelo gerado, mantendo aliases para os
  componentes atuais até a migração estar completa.

### Limites no servidor

| Limite | Valor sugerido | Onde aplicar |
|---|---|---|
| Tamanho de upload por arquivo | 10 MiB imagem, 30 MiB mesh | FastAPI `Request` body limit |
| Tamanho total do payload JSON | 64 MiB | nginx `client_max_body_size` |
| Multipart opcional | 128 MiB | quando o upload for binário |
| Fila máxima | 64 | `PriorityQueue` + `put_nowait` controlado |
| SSE buffer por cliente | 8 eventos | snapshot coalescido |
| Conexões SSE simultâneas | 16 | semáforo em `manager.subscribe_list` |

### Capabilities e presets

`GET /v1/capabilities`:

```json
{
  "modes": {
    "text": { "available": true, "requires": ["text_to_image"] },
    "image": { "available": true },
    "multiview": { "available": false, "reason": "model_not_loaded" },
    "texture": { "available": true }
  },
  "presets": {
    "fast":     { "steps": 5,  "guidance": 5.0, "octree_resolution": 192 },
    "balanced": { "steps": 50, "guidance": 5.0, "octree_resolution": 256 },
    "detailed": { "steps": 100,"guidance": 7.5, "octree_resolution": 384 }
  },
  "limits": {
    "image_bytes": 10485760,
    "mesh_bytes": 31457280,
    "queue_depth": 64
  }
}
```

A UI lê `/v1/capabilities` no boot e desabilita abas indisponíveis com
explicação ("modelo multiview não carregado").

### Progresso por etapa

`JobResponse.stage` (`string | null`) e `JobResponse.stage_progress` (`float`)
opcionalmente preenchidos pelo manager; o worker emite eventos
`{"event": "stage", "data": {...}}` no SSE por trabalho. UI mostra etapas
"carregando modelo -> gerando geometria -> texturizando -> exportando" com
barra de progresso quando houver dados reais.

### Serviço de inferência compartilhado

Hoje `launcher.py` e `hy3dgen/inference.py` têm classes diferentes para
gerenciar modelo, offload e cache. Extrair um `inference_service.py` único
com:

```text
InferenceService
+-- load_shape(model_id, subfolder)
+-- load_texture(model_id)
+-- load_t2i(model_id)
+-- unload(model_id)
+-- generate(payload) -> AsyncIterator[StageEvent]
+-- capabilities() -> Capabilities
+-- memory_pressure() -> float
```

Launcher e API passam a chamar este serviço; diferenças de UX (CLI vs HTTP)
ficam em camadas finas.

## 7. Critérios de aceite globais

- API: mypy + ruff limpos em `hy3dgen/api` e `tests`; cobertura de
  branches >= 80 % nas rotas, fila, persistence e capabilities.
- Frontend: `tsc -b && vite build` zero erros; ESLint zero erros e
  zero warnings; testes Vitest + Playwright verdes em CI; bundle inicial
  < 200 kB gzip.
- UI/UX: contraste mínimo 4.5:1 em texto normal; navegação completa por
  teclado; axe-core sem violações sérias; smoke visual em 360/390/768/1024/1440.
- Operação: `docker compose config --quiet` aprovado; `python -m build`
  produz wheel + sdist válidos; instalação limpa do backend sem Torch
  continua funcional para `/health` e `/metrics`; GPU validada com
  fluxos dos quatro modos.
- Documentação: `POLYFORGE_README.md` com quickstart real; nova página
  `docs/polyforge/ROADMAP.md` apontando capacidades vs. roadmap;
  `docs/polyforge/BENCHMARKS.md` com tabela de tempos.

## 8. Não-objetivos desta fase

- Migração para Postgres ou Redis. A heap atual (manager + SQLite) cobre o
  cenário de estúdio local.
- Editor 3D completo. Continua fora de escopo.
- Multi-GPU ou sharding. Mantemos 1 GPU por processo; paralelização via
  processos isolados é responsabilidade do operador.
- Reescrita do frontend em outro framework. React 19 + Vite 7 + Tailwind 4
  seguem adequados.

## 9. Resultado esperado

Ao final da Fase 2 o PolyForge deve:

- Expor uma área de criação centrada no resultado 3D, com etapas visíveis
  e navegação clara entre criar, biblioteca, sistema e configurações.
- Operar de forma coerente em ambiente local e em container, com presets
  calibrados e capabilities expostas.
- Garantir continuidade de tipos entre backend e frontend, com geração
  automática a partir do OpenAPI.
- Ter testes E2E cobrindo os fluxos críticos e validação real em GPU.

A Fase 2 preserva o investimento da Etapa 1 e adiciona a camada de produto
que faltava para o PolyForge ser usável como estúdio local por usuários não
técnicos, sem perder a precisão dos controles avançados.
